Beta Authoring Pattern: Sequential Steps with a State Machine

Status: Recommended pattern for the closed beta. Audience: Trainer-facing. The "Authoring pattern" section below is written to be lifted directly into client-facing training; the "Why this pattern (trainer note)" section is internal context and should not go to clients as-is.

Authoring pattern

When a training experience follows a defined sequence of steps that the learner completes in order, build the sequence with a State Machine (Named) — one named state per step.

This gives every step three predictable parts:

  • Step entry — an On State Cause for the step's state. Wire anything that should happen when the step begins (prompts, highlights, enabling the objects the learner needs).
  • Step logic — the Cause-Effect chain the learner drives during the step (interact, grab, collide, move objects, and so on).
  • Step completion — a Go to Named State Effect as the last node in the chain, pointing at the next step's state.

Because completion is the last thing the chain does, every effect before it finishes first. A move that runs over time completes, its follow-on effects fire, and only then does the step advance. The transition is in the same chain as the work, so it always runs in order.

Setup

  1. Open the Spark Browser. Under Config Sparks, drag a State Machine (Named) into the Configs panel.
  2. Rename the Instance for clarity — for example, "Procedure".
  3. Add one named state per step. Name them after the steps themselves ("inspect-panel", "close-valve", "confirm") so the Behaviors tab reads as the procedure.

Wiring each step

For a step named close-valve that the learner completes by interacting with a valve, after which the valve animates shut and a confirmation highlight turns on:

On State (close-valve) → Converse (NPC, "Close the valve.")

Interacted (valve) → Move (valve, to closed)
                   → Highlight (confirm marker, on)
                   → Go to Named State (confirm)

The Go to Named State node is the terminal node for the step. Place it last, after every effect the step needs to run.

Branching

A step can lead to more than one next step. Wire a separate chain for each outcome, each ending in its own Go to Named State:

Interacted (correct tool) → Go to Named State (use-tool)
Interacted (wrong tool)   → Converse (NPC, "Not that one.") → Go to Named State (retry)

Completing the procedure

The final step's chain ends in a Change Chapter Effect (to advance to a debrief) rather than another Go to Named State.

Things to know

  • The first state fires at Chapter load. The On State Cause for the first named state fires automatically when the Chapter starts, before any interaction. Use it to set up the opening step.
  • Transitioning to the current state does nothing. A Go to Named State that targets the state already active does not re-fire its On State. Always advance to a different state.
  • State does not persist across Chapters. Keep a full procedure within one Chapter, or carry a value forward with a persistent Datum Spark if the next Chapter needs it.
  • No learner-facing step checklist. This pattern drives the logic, but it does not display a "Step 2 of 5" list to the learner. If a scenario needs a visible step list on screen, build that UI explicitly. (Verify whether any beta scenario actually requires this before relying on the pattern.)

Warning: do not reorder or delete states after wiring

State references in a Named State Machine resolve by position in the states list, not by name — despite the names you see in the dropdowns. Reordering or deleting a state silently re-points every Go to Named State and On State Enter that targeted a state at or after the change. The wiring still shows a valid state name, so the corruption is invisible until the procedure runs in the wrong order. (Runtime bug: BLDR-97.)

This compounds with a second limitation: the list editor's Remove button only ever deletes the last state — there is no per-row delete (BLDR-96). Deleting any other step forces you to drag it to the end first, and that reorder is exactly what corrupts references.

Practical guidance for the beta:

  • Lock the step list before wiring. Decide the full sequence of states first. Add states in final order, then wire. Reordering after wiring is the trap.
  • To remove a middle step, neutralize it in place — do not delete it. Leave the slot where it is (preserving every index), rename it to something like UNUSED, and unwire its On State Enter. The sequence passes through a harmless no-op and not a single reference shifts. Only do a true delete when it is the genuine last state and nothing points at it.
  • If you must reorder or delete: afterward, open every Go to Named State and On State Enter from the change point onward and re-select the correct state by name. Cross-check against your written step list — the dropdowns will look fine but hold the wrong target.

Why this pattern (trainer note — internal)

Two reasons to teach this rather than Step Manager during the beta:

1. It avoids a known Step Manager defect. Step Manager currently completes a step by polling, one frame after the triggering interaction, on a path separate from the behavior graph. When the same interaction both completes the step and drives a multi-frame or chained effect, the step can advance before the chain finishes, and the remaining effects are silently dropped. Tracked as BLDR-77. The State Machine has no such race: its transition runs synchronously, in chain order.

2. It will not change under the learner. The State Machine is stable and is not on the redesign roadmap. Everything taught with it survives untouched. Step Manager is being reshaped (see context/step-manager-race-design-brief.html), so anything taught with it now risks being re-taught later.

Forward compatibility

This pattern is the future Step Manager model in everything but name. When the redesign lands, the swap is close to one-for-one:

Beta pattern (State Machine) After Step Manager redesign
one named state per step one step
On State Cause step entry / on-enter
Go to Named State as the last node outcome node (terminal sink)
final step → Change Chapter final outcome → Chapter advance

The graph shape does not change. The transition stays the last node in the chain. Rebuilding into the new Step Manager is re-housing the same structure in the panel, not relearning how to think about steps. Teaching the "completion is the last node in the chain" habit now is what makes that later swap nearly free.

What you give up versus Step Manager

  • No automatic outcome table — transitions are wired by hand.
  • No panel-level view of how steps connect; the structure lives in the states and the graph.
  • No auto-provisioned nodes; you add each Go to Named State yourself.

All acceptable for the beta, and all recovered when the redesigned Step Manager arrives.
