Project 2 — Tire Change

Reconciled to the as-built scenario · Updated June 23, 2026 · Sessions 1–2 (Project 1)

This doc describes the scenario as actually built in the Tire Change book (~/Documents/Builder101/Builder 101- TireChange.pixob, 8 chapters). It supersedes the earlier outdoor/floor-jack/9-step draft, which was never built. The build is the source of truth. Trainer-facing build sequence: tire-change-checkpoints.md.

Overview

A single-Chapter training module that walks the learner through changing a wheel on a passenger vehicle raised on a two-post automotive lift, in an indoor garage. Eleven ordered steps, gated in sequence, with on-screen step tracking and per-step voiceover. The learner progresses by interacting with physical objects — the lift, the lug wrench, the wheels, and the lug nuts.

This is Session 1–2's hands-on build — the program's first project. Participants follow along with the trainer and end up with a complete, playable, published experience by the end of Session 2.

The garage shell is shared with the Hazard Recognition project — same walls, lighting, racks, and table. As of the July 24, 2026 split, the two scenarios ship as separate Books (Builder 101- TireChange.pixob and Builder101_HazRec.pixob), each carrying its own copy of the garage from the common ancestor — so "same room" is a shared lineage, not a shared file.

Why this scenario

  • Universally understood — no domain expertise required of any trainee
  • Order-dependent procedure that maps cleanly onto a one-state-per-step model
  • Discrete tool-to-target interactions (wrench on lug nuts, wheel on hub) that map cleanly onto the Cause → Effect model
  • No particles, fluids, or physics edge cases — buildable with the current Builder feature set
  • Establishes the shared garage environment (Project 2, Hazard Recognition, reuses it later) — one room, two experiences. Session 1 hands over the room pre-built so live time goes to logic, not set dressing

Procedure (as built — 11 steps + completion)

The Step Manager exposes these as the learner-facing step list:

  1. Raise the lift
  2. Grab the wrench
  3. Use the wrench (loosen lug nuts)
  4. Replace the wrench
  5. Remove the old wheel
  6. Place the new wheel
  7. Replace the lug nuts
  8. Grab the wrench (second time)
  9. Tighten the lug nuts
  10. Return the wrench
  11. Lower the lift
  12. Lesson complete

The procedure is linear — each step has a single outcome leading to the next. There is no wrong-order failure branching in the current build (see Open Questions).

Architecture

The logic is layered across two State Machines plus a Step Manager. This separation is the single most important thing the build teaches:

  • Steps State Machine (Named) — the procedure spine. Twelve named states, one per procedure beat: Lesson Start → Lift Raised → Wrench Grabbed 1 → Wrench Used 1 → Wrench Replaced 1 → Old Wheel Removed → New Wheel Placed → Lug Nuts Replaced → Wrench Grabbed 2 → Lug Nuts Tightened → Wrench Replaced (2) → Lift Lowered. Each step's work chain ends in a Go to Named State as its terminal node, per the recommended beta pattern. This drives everything — including lift position, which the spine carries via its Lift Raised / Lift Lowered states rather than a separate tracker.

  • Lug Nuts States State Machine — lug-nut location. On Wheel / On Table.

  • Step Manager — the visible tracker. Each of its steps completes on a condition that reads the Steps State Machine's current state (e.g., step "Use Wrench" completes when the Steps machine is at Wrench Used 1). The Step Manager observes; the State Machine drives. This is the race-safe configuration — it avoids the Step Manager polling defect (PLATFORM-2212) because the transition runs synchronously in the State Machine's chain.

Each step also fires a voiceover clip (VO_RaiseLift, VO_GrabWrench1, and so on — 12 total) on step entry, and the wiring is organized into Sub Graphs to stay readable.

Environment

Indoor garage: two-post lift, tool racks, work table, walls with a door, decals, interior lighting plus a sky/sun. Deliberately the same shell as Hazard Recognition — participants see how one environment supports two different training experiences.

Assets

PM provides a complete asset pack: sedan (intact and right-rear-wheel-removed variants), two-post lift, lug wrench, spare/replacement wheel, lug nuts. Same pack across every cohort. These are pre-placed in the checkpoint Books so Session 1 stays focused on the core model — learners do their first hands-on GLB import in Project 2 (Hazard Recognition), not here.

Stretch goals (if time allows in Session 2)

  • Wrong-order handling — a failure branch if the learner attempts a lift-down step while raised, or vice versa (the Steps spine already tracks Lift Raised / Lift Lowered to gate this)
  • Highlight Effect directing attention to the next correct tool or target
  • Lug nut rotation animation during loosen/tighten
  • Audio feedback on success/failure beats
  • A summary screen in the completion Chapter
