Building Your First Two Modules

Two complete training modules — a guided procedure and a scored assessment

This syllabus walks you through building two complete, playable training modules in Pixo Builder — Tire Change, an ordered step-by-step procedure, and Hazard Recognition, a randomized spot-the-hazard assessment. Build them in order: Tire Change teaches the core model, and Hazard Recognition builds advanced features on top of it. By the end you'll have two experiences you built yourself — and the patterns behind almost anything you'll want to author next.

Before you start

  • Builder installed and opening, with your account signed in.
  • A Pixo Platform account — it's how you'll publish and test your finished modules.
  • The two design documents open alongside you — they're the spec for what you're building. Read each one before you build that project: Tire Change step list · Hazard Recognition design document.
  • The documentation — each unit below lists what to read. The docs do the detailed teaching; this syllabus is the map.

Work at your own pace. Each unit ends with something playable, so you always have a checkpoint to return to. If a unit's concepts feel new, read its listed docs before building — they're chosen to make that unit achievable.

Project 1 · Tire Change — a guided procedure

An ordered procedure: the learner changes a wheel on a lifted vehicle, one gated step at a time. This project teaches the entire core model of Builder.

Unit 1

Foundations & your first interaction

Get to the moment where you drag something into a scene, wire it yourself, press play, and watch it work.

What you'll build

  1. Open the garage scene and move around it in Map Explorer.
  2. Drag a Spark into the scene to create an Instance; find it in the Instances pane.
  3. Set an exact value in the Traits Panel and watch it update.
  4. Wire your first behavior: Interacted → Highlight. Test it in play mode.
  5. Add a second Effect on the same Cause (Play Audio), then wire the lift to raise on interact.

New concepts

Spark vs. Instance · Cause → Effect → wire · Traits · edit mode vs. play mode · the Audio Config Spark.

Read

Getting Started Guide · First Success Walkthrough · Spark vs. Instance · Spark types overview · Modifiers reference · Edit Mode and Play Mode.

Unit 2

The procedure spine, tracking & publishing

Turn the scene into a real, ordered procedure that knows where the learner is — then publish it and test it on a device.

What you'll build

  1. A State Machine as the procedure spine — one state per step, in order.
  2. Each step's effects hanging off the spine: animation, movement, grabbing and releasing tools, collision/trigger detection, rotation, mesh swaps, and attaching objects.
  3. Sub Graphs to keep the wiring readable as it grows.
  4. A Step Manager that shows the learner which step they're on.
  5. Screen-space UI and a crosshair.
  6. Publish to the Pixo Platform, then test the finished module on your device.

New concepts

State Machine (object state, then the procedure spine) · Sub Graphs · Step Manager as an observer · Screen Space UI + Crosshair · Change Chapter · publishing and lifecycle stages (Debug → QA → UAT → Release).

Read

Common Patterns (State Machines) · Step Manager reference · Sub Graphs reference · Publishing & Lifecycle Stages · Config Sparks reference.

The pattern travels. A three-step procedure and a thirty-step procedure are the same shape. Once Tire Change works end to end, you own the pattern behind every sequential training experience you'll build.

Project 2 · Hazard Recognition — a scored assessment

The same garage, a different kind of training. Five spots around the room; three are hazards each run, chosen at random. The learner clicks what they think is unsafe and gets scored. This project is the same primitives from Project 1, turned to a new shape — and it introduces the advanced features.

Unit 3

Import, parallel state & feedback

Instead of one state machine stepping through a sequence, run several at once — one per spot — each tracking whether the learner has caught it.

What you'll build

  1. Import your first GLB asset and place it in the scene.
  2. Place the five spots, each with a hazard version and a safe version at the same position.
  3. On one spot, a four-state machine: safe/hazard × clicked/unclicked.
  4. Two wired outcomes off one click — a correct catch and a false positive.
  5. Chapter Started initialization so the scene comes up in a known state.

New concepts

Importing assets (GLB → Spark) · parallel State Machines · branching feedback (correct vs. incorrect) · Chapter Started.

Read

Importing Assets Guide · Common Patterns (parallel State Machines) · Randomizer / Modifiers reference · Datum Spark reference.

Unit 4

Randomization, scoring & world-space UI

Make the scene different every run, keep score, and show the result — then publish your second, richer module.

What you'll build

  1. A Randomizer that makes exactly three of the five spots hazards at the start of each run.
  2. Three Datums that keep score: hazards to find, hazards caught, and mistakes.
  3. Datum Viewers that display those values live.
  4. World-space UI — a Billboard with Text and a Button — for instructions and the end-of-run score.
  5. The catch/mistake pattern extended across all five spots, and a Done button that reveals the tally.
  6. Publish and test on your device.

New concepts

Randomizer (non-deterministic scenes) · Datum Sparks & Datum Viewers · world-space UI with Symbol Sparks (Billboard / Button / Text).

Read

Datum Spark reference · Symbol Sparks reference · Randomizer / Modifiers reference · Common Patterns (scoring & feedback).

Testing a random scene. Because the hazard set changes every run, play it several times — you're confirming the behavior holds no matter which three spots come up.

What's next — your own module

With both modules built, you've used the full core model and every advanced feature: state machines (sequential and parallel), branching logic, randomization, scoring with Datums, and world-space UI. The natural next step is to build a short module of your own, with your own assets — pick a real task from your work, sketch a quick design document for it first (the two you read are the model), then build it, publish it, and test it on a device. That's the whole skill.
